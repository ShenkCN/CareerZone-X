## 2. 技术栈和选型理由

| 层 | 技术 | 为什么用它 | 代价/边界 |
|---|---|---|---|
| 用户界面 | Streamlit | 纯 Python、表单/卡片/上传快、个人工具不需要前端工程 | 每次交互 rerun，复杂布局要用 CSS；不是高并发产品 |
| API | FastAPI | 类型校验、Swagger、路由清晰、易测试 | 需要自己写鉴权/限流 |
| ASGI | Uvicorn | 轻量、单机足够 | 单进程；生产需反向代理 |
| ORM | SQLAlchemy 2.x | SQLite/MySQL 统一写法、事务清晰 | 复杂查询仍需手写表达式 |
| 数据库 | SQLite 默认 | 零安装、单文件、易备份 | 不适合多进程高并发写 |
| 可选数据库 | MySQL 8 | 面试可讲、客户端工具成熟 | 本机 WSL 不稳定，默认不用 |
| 密码 | Argon2id | 抗 GPU 爆破，比 PBKDF2 更现代 | 依赖 C 扩展，安装略重 |
| 会话 | 服务端随机 token + 哈希 | 不把密码存前端；可撤销 | Cookie 本机自用非 HttpOnly |
| 模型 | DeepSeek HTTP | 用户已有 Key；直接 POST 稳定 | 需要网络/额度；限流时降级规则 |
| 向量 | Chroma | 相似职位检索；本地持久化 | 本机 DLL 限制，默认 hash-384 降级 |
| 采集 | Manifest V3 扩展 | 只在用户点击/浏览时读当前页 | 不能自动翻页；平台条款限制 |
| 测试 | pytest + Ruff | 接口回归、代码规范 | 前端 Streamlit 仍靠 smoke |

## 3. 为什么不用“后台自动爬虫”

这是产品的第一约束，不是技术做不到。

- BOSS/猎聘等平台没有给个人开放全量职位 API；
- 服务端自动登录、自动翻页、绕验证码属于自动批量抓取；
- 会触发风控，也可能违反平台条款；
- 即使“个人自用”，也不等于平台授权。

所以架构选择：

    不做：服务端 requests/Playwright 自动翻页、自动登录
    做：浏览器扩展，用户点击或滚动当前页时读取可见 DOM

这条边界决定了产品上限：不是“全自动聚合器”，而是“半自动求职工作台”。  
如果面试被问“为什么不做全自动”，就答这个取舍，不要包装成技术限制。

## 4. 核心数据流

### 4.1 注册/登录

    flowchart TD
        A[注册: 账号/密码] --> B[密码 Argon2id 哈希]
        B --> C[状态 pending]
        C --> D[管理员审核]
        D -->|通过| E[状态 active]
        E --> F[登录]
        F --> G[生成随机会话 token]
        G --> H[数据库存 token 哈希]
        H --> I[Streamlit 保存 token/Cookie]

### 4.2 采集职位

    flowchart TD
        A[用户打开招聘页面] --> B{当前页类型}
        B -->|列表| C[扩展读卡片 + 当前选中详情]
        B -->|详情| D[扩展读完整 JD]
        C --> E[POST /api/jobs/import]
        D --> E
        E --> F[URL/指纹去重]
        F --> G[新增或更新]
        G --> H[写 ImportBatch + JobCapture]
        H --> I[写审计: 新增/更新/跳过/批次]
        I --> J[职位板显示本批重复率]

### 4.3 搜索 + AI 初筛

    flowchart TD
        A[筛选条件] --> B[SQL 条件: 关键词/城市/薪资/... + 本人未清空 + 至少一个 active capture]
        B --> C[先取最多 1200 候选]
        C --> D[排序/分页 最多 1000]
        D --> E{开启 AI 初筛?}
        E -->|否| F[直接返回列表]
        E -->|是| G[最多取前 300 条]
        G --> H[40 条/组, 3 组并发]
        H --> I[DeepSeek 返回 JSON]
        I --> J[写 screenings]
        J --> K[列表展示分/档位/理由]

### 4.4 两轮深度分析

    flowchart TD
        A[点进职位详情] --> B{JD 完整?}
        B -->|否| C[显示警告, 禁用分析]
        B -->|是| D[第一轮: JD 结构化]
        D --> E[第二轮: 画像匹配]
        E --> F[匹配分/缺口/风险/简历角度]
        F --> G[按 profile_hash 缓存]

### 4.5 按用户清空职位

    flowchart TD
        A[扩展弹窗点清空] --> B[二次确认]
        B --> C[SQLite 备份到 storage/backups]
        C --> D[标记当前用户 JobCapture.cleared_at]
        D --> E[搜索 SQL 排除本人已清空]
        E --> F[无自己副本的用户也隐藏; Job 不删除]

### 4.6 恢复职位

    flowchart TD
        A[用户在历史页选一条/几条/全部] --> B[POST /jobs/restore-request]
        B --> C[RestoreRequest pending]
        C --> D[管理员账号管理页批准]
        D --> E[清空 cleared_at]
        E --> F[用户职位板重新出现]

### 4.7 官方 API（预留）

    flowchart TD
        A[官方授权/Key] --> B[official_source.fetch_official_jobs]
        B --> C[POST /api/admin/official/collect]
        C --> D[upsert_job + import_batches]
        D --> E[复用 AI 初筛/分析]

> 没有官方授权时端点返回 503，不自动爬取。

## 6. 关键设计取舍

### 6.1 为什么 SQLite 默认

- 单用户、零安装；
- 单文件备份；
- 本机 WSL MySQL 曾反复被外部进程停止，导致随机 500；
- MySQL 代码保留，稳定后可切。

### 6.2 为什么 Chroma 降级

- 本机 DLL 策略拦截 torch/regex；
- 默认 hash-384（字符 bigram + 英文 token），不是最强语义，但能离线跑；
- 需要更强语义时设 VECTOR_TRY_MODEL=true 并承担模型下载/依赖。

### 6.3 为什么 AI 分 40 条/组、3 并发

- 1000 条一次调用会截断 JSON；
- 40 条/组，8192 输出 token；
- 3 路并发缩短等待；
- 每页最多 300 条，其余按需分析，控制 Token。

### 6.4 为什么清空改成“按采集关系隐藏”

- 多用户共享职位库时，硬删除会误伤别人；
- 清空只写 JobCapture.cleared_at，不删除 Job；
- 搜索要求职位至少有一个未清空的 capture：A 清空后，没有自己副本的 B 也看不到；B 自己采过则保留；
- 仍保留 SQLite 备份，但真正的恢复靠管理员恢复接口；
- 旧版 253 条硬删除发生在备份/关系表之前，已无法恢复——这是真实教训。

## 7. 项目为什么接近 1.8GB

| 目录 | 约占用 | 说明 |
|---|---:|---|
| .venv | 1.75GB | Python 依赖，不是业务代码 |
| storage | 14MB | SQLite/Chroma/上传/日志 |
| dist | 1.7MB | 打包中间目录 + ZIP |
| 代码 | 约2MB | backend/frontend/docs 等 |

.venv 里主要大头：

    torch 518MB
    kubernetes 117MB
    scipy 113MB
    transformers 110MB
    pyarrow 89MB
    sympy 72MB
    pandas 66MB
    chromadb_rust_bindings 60MB
    plotly 58MB
    onnxruntime 52MB

这些大多来自 RAG 可选依赖；当前默认 VECTOR_TRY_MODEL=false，实际用 hash 向量。  
清理 __pycache__ 不会把 1.75GB 变成几百 MB；要显著变小，只能卸载 RAG 可选依赖或删除 .venv 重建。  
项目暂停时保留 .venv，方便下次直接恢复；如果确定不再用 RAG，可另做一次精简。

## 8. 暂停/恢复

暂停：

    # 关闭 API/UI（见 README 或 start.ps1 的说明）
    # 移除登录自启动（可选）
    .\scripts\remove_autostart.ps1

恢复：

    cd "D:\CareerZone X"
    .\start.ps1

自启动重新安装：

    .\scripts\install_autostart.ps1
